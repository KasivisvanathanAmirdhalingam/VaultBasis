Handover directive for the new developer
Give the following as the controlling directive. I would retire PRES-003 rather than ask another developer to keep repairing it.
MMP11-UX-001 — ENTERPRISE PRACTITIONER EXPERIENCE CONVERGENCE
Mission
VaultBasis is an independent evidence-assurance product intended for tax practitioners and other users operating in high-trust, regulated professional environments.
The product must create confidence before the user understands its cryptography or architecture.
The experience must communicate:
independence → determinism → evidence preservation → verifiability → professional boundaries.
The user should never have to understand the internal release architecture, engineering terminology, implementation topology, localhost routing, development history, MMP/RC nomenclature or infrastructure in order to use or trust the product.
This is not a cosmetic redesign.
It is the final convergence of:
brand + information architecture + interaction design + accessibility + functional journeys + Edge/web continuity.
Absolute technical boundary
Do not modify:
- deterministic reconciliation semantics;
- canonicalization;
- decimal semantics;
- supported-source interpretation;
- outcome-state rules;
- provenance semantics;
- Outcome Receipt schema;
- receipt signing;
- signature verification semantics;
- Golden Corpus;
- deterministic test vectors;
- evidence contract;
- unresolved-information behavior.
The assurance kernel remains authoritative and isolated.
UI code may invoke those capabilities. It must not reinterpret them.
Day-one success definition
A CPA/EA seeing VaultBasis for the first time should be able to answer within roughly one minute:
What does this product do?
Independent reconciliation of supported broker and tax-ledger information.
Why would I use it?
To independently identify agreements, differences and unresolved evidence and retain a portable verifiable record.
What doesn't it do?
It doesn't decide tax correctness, legal compliance, source truth or professional judgment.
Where does my evidence go?
The Edge evidence-processing boundary is local as declared; website/access/distribution activities are separate.
What do I do next?
Request access, evaluate the product, or verify an Outcome Receipt.
And the interface should visually communicate that this is professional assurance software—not a developer demonstration.

Accessibility is a release gate, not a checkbox
I would target WCAG 2.2 AA as the engineering accessibility baseline.
Do not claim “ADA compliant.” ADA applicability/compliance is a legal determination; engineering can demonstrate conformance evidence against a declared accessibility standard.
Create:
MMP11-A11Y-001 — WCAG 2.2 AA Qualification
Test every public page, access modal, verifier and practitioner Edge UI for:
- semantic landmarks and heading hierarchy;
- keyboard-only operation;
- no keyboard traps;
- logical focus order;
- visible focus indicators;
- modal focus containment and restoration;
- Escape behavior;
- accessible names for icon-only controls;
- form labels/instructions/errors;
- programmatic error association;
- status messages announced appropriately;
- color contrast;
- text contrast;
- non-text contrast;
- zoom to 200%;
- text spacing;
- reflow at 320 CSS px;
- target sizes;
- hover/focus equivalence;
- skip-to-content;
- page titles;
- link purpose;
- duplicate IDs;
- language declaration;
- reduced-motion handling;
- accessible downloads;
- tables with correct headers;
- mobile keyboard/touch behavior.
Automate with axe-core/Playwright where possible.
But automated accessibility scanning cannot qualify accessibility alone. Add manual keyboard testing and at least VoiceOver on macOS/iOS or equivalent screen-reader testing.
Zero serious/critical automated accessibility violations is required, but it is not sufficient.

Time protection
I would also impose a hard rule now: do not spend another two days polishing the website while Associate work waits.
Split execution.
Track A — new UX developer: web + Edge experience convergence.
Track B — release/security: artifact qualification, entitlement/access-control production checks.
Track C — MMP-1.5/MMP-2: documentation, ledger, architecture and non-conflicting research/prototyping can continue, but nothing touches the MMP-1.1 assurance kernel/release branches.
Associate-001 begins immediately after the bounded external-release gates pass. Don't hold it for P2 aesthetic perfection. But don't send an associate into a product with broken navigation, incomplete access, inaccessible controls or contradictory branding either.
Your current reaction is itself useful acceptance evidence: if the founder who knows every architectural distinction is repeatedly confused or repelled by the navigation and presentation, sending an uninformed practitioner into it would give you noisy product-validation evidence rather than clean evidence about whether the underlying problem is valuable.
The next developer's job is therefore not to make VaultBasis prettier. It is to make the interface disappear between practitioner intent and the deterministic assurance system. That's the standard I would use for the handover.
